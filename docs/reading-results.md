# 대시보드에서 데이터를 읽고 설정을 고르는 방법

서빙 결과에서 답할 질문은 “이 모델이 이 정도 부하를 받을 때, 응답 시간 목표를 지키면서 얼마나 처리할 수 있는가?”다. Pod 관측은 운영 중의 징후를 확인하고, 커널 Roofline은 장비에서 계측한 연산의 성능 상한을 살펴보는 데 사용한다.

## 1. 파일 종류에 맞는 화면 선택

프로젝트의 `web/index.html`을 브라우저에서 연다. 서버나 클러스터에 접속할 수 없는 PC에서도 이미 수집한 데이터를 열 수 있다.

| 가지고 있는 것 | 어디에 넣는가 | 화면에 표시되는 단위 |
|---|---|---|
| `runs.csv`, `html.json`, 호환 벤치 JSON | **서빙 분석 → 측정 파일 열기**. 비교할 파일을 한 번에 선택 | 벤치마크 실행·서버 설정 |
| `kubectl-summary.json` | **원격 수집 → Pod 관측 파일 열기** | Pod 한 개, 모델·엔진 라벨별 시계열 요약 |
| 프로파일러의 커널 계측값 | **커널 Roofline**에 최대 연산 성능, HBM 대역폭, 연산량, HBM 읽기+쓰기, 시간을 입력 | 동일 칩 범위에서 같은 연산 구간 |

새로 파일을 열면 기존 선택 데이터가 교체된다. 가상 예시와 실측은 따로 열고, 일반 서버 로그는 먼저 [수집기와 변환 방법](usage.md)을 확인한다.

## 2. 실측 CSV 한 행 읽기

**서빙 분석 → 측정 파일 열기**에서 [mac-smoke.csv](../examples/mac-smoke.csv)를 연다. 한 행은 같은 조건에서 수행한 벤치마크 한 번이다. 이 행에는 모델 기동과 워밍업 이후 보낸 요청 5건의 결과가 담겨 있다.

| 실측 항목 | 값 | 의미 |
|---|---:|---|
| 첫 응답 지연 p95 | 286.8ms | 요청 전송부터 첫 텍스트 수신까지. 이 점검은 표본 5건에 최근접 순위 방식을 사용해 가장 느린 요청이 p95다. |
| 출력 청크 간격 p95 | 33.6ms | 첫 청크 이후 연속 출력 사이의 시간. 이 점검에서는 요청당 텍스트 청크 12개와 출력 토큰 수 12개가 일치하는지 검사했다. |
| 전체 출력 처리량 | 18.91토큰/초 | 5건의 출력 60토큰을 워밍업 제외 측정 구간 약 3.17초로 나눈 값이다. |
| 실행 상태 / 품질 | `ok` / `unknown` | 정해진 부하를 완료했다. 생성 문장의 품질 평가는 별도로 수행한다. |

이 수치는 **해당 맥북·CPU 빌드·입력 길이·부하·설정 한 가지의 기준값**이다. ‘추천 없음’이 보이면 결과 표의 판정 열을 확인한다. `정합성 통과 설정만 추천`이 기본으로 켜져 있다. 성능 후보만 탐색할 때 체크를 해제하면 미확인 설정도 후보로 검토할 수 있다. 품질이 통과로 바뀌는 것은 아니다.

## 3. 조건 하나를 바꾸고 추천이 달라지는 이유 보기

**데이터 가이드 → 예시로 돌아가기**를 누른다. 이 절의 수치는 화면에 내장된 **가상 TPU 예시**다. 동시 요청 수 `1024`, 최대화할 처리량 `출력 토큰/초`, p95 첫 토큰 지연(TTFT) 목표 `1500ms`, p95 토큰 간 지연(ITL) 목표 `50ms`를 선택한다.

다음 세 후보에서 시퀀스 상한은 1,024, 문맥 상한은 8,192다. 달라지는 값은 한 스텝의 토큰 예산인 `max_num_batched_tokens`다.

| 토큰 예산 | p95 TTFT | p95 ITL | 출력 토큰/초 | ITL 목표 50ms에서 판정 |
|---:|---:|---:|---:|---|
| 4,096 | 1,061ms | 40.4ms | 1,540 | 충족 |
| 8,192 | 970ms | 46.5ms | 1,720 | 추천 |
| 16,384 | 924ms | 59.6ms | 1,780 | ITL 초과 |

목표를 50ms에서 **45ms**로 줄이면 추천 예산은 **4,096**이 된다. 8,192는 4,096보다 처리량이 약 11.7% 높지만, 연속 출력 사이의 지연이 새 목표를 초과한다. **파라미터를 바꾼 효과**에서 기준 설정과 변경 항목을 고르면 나머지 두 상한을 고정한 쌍을 볼 수 있다. **같은 설정에서 동시 요청 수를 늘리면**에서는 서버 설정을 고정하고 클라이언트 부하에 따른 변화를 본다.

실제 결과는 같은 모델 리비전·토크나이저·정밀도·장비·입출력 길이·동시 요청 조건부터 맞춘다. 대시보드는 반복별 처리량의 중앙값과 반복별 p95 중 최댓값을 쓴다. 실패한 반복이나 정합성 실패가 있는 설정은 추천 대상에서 제외한다. 화면이 고른 값은 **측정한 후보와 입력한 목표 안에서의 최선**이다.

## 4. Pod에서 병목의 단서 찾기

**원격 수집 → Pod 관측 파일 열기**에서 [kubectl-summary.json](../examples/kubectl-summary.json)을 선택한다. 가상 예시의 대기 요청은 처음 0, 최대 12, 마지막 0건이다. 예약한 KV 캐시의 최고 사용률은 80%, 관측된 선점 증가량은 0이다.

이 결과에서는 관측 중 대기가 생겼다가 마지막 표본에서 해소됐다는 것까지 알 수 있다. 대기가 오래 쌓이거나 첫 응답도 늦어졌다면 `metrics.jsonl.gz`에서 **같은 UTC 시각, 같은 모델·엔진**의 실행 요청·대기 요청·KV 사용률·선점 증가를 맞춰 본다. 표에 표시한 최댓값은 서로 다른 시각에서 나올 수 있다. Pod가 교체된 구간이나 값을 읽지 못한 구간은 정상 수치와 구별한다. [실제 Pod 연결 절차](kubectl-quickstart.md)

## 5. 커널 Roofline 읽기

**커널 Roofline**의 기본 입력은 단위 확인용 가상 예시다. 칩의 최대 연산 성능 **200 TFLOP/s**, HBM 대역폭 **2 TB/s**, 커널 연산량 **60 GFLOP**, HBM 읽기+쓰기 **1.2 GB**, 실행 시간 **1ms**를 넣는다.

| 계산 | 예시 결과 |
|---|---:|
| 데이터 1바이트당 연산 수 = 60 GFLOP ÷ 1.2 GB | 50 FLOP/byte |
| 이 구간의 이론 상한 = min(200, 2 × 50) | 100 TFLOP/s |
| 측정 성능 = 60 GFLOP ÷ 1ms | 60 TFLOP/s |
| 측정 성능 ÷ 이론 상한 | 60% |

이 예시의 연산 집약도에서는 HBM 대역폭이 이론 상한을 결정한다. 실제 점과 상한 사이에 남은 40%의 원인은 커널 프로파일에서 추가로 확인한다. 실측에는 GPU Nsight Compute 또는 TPU XProf 등에서 **동일 연산 구간·칩 수·정밀도** 기준으로 뽑은 값을 사용한다. [프로파일 CSV 변환 명령](usage.md) · [XProf Roofline 정의](https://openxla.org/xprof/roofline_model)

## 실제 GPU·TPU 결과를 정리할 때

같은 조건의 H200·Ironwood 기준 설정을 먼저 비교한 뒤, 각 장비에서 같은 서비스 목표를 만족하는 최고 실측 처리량을 별도로 비교한다. 결과를 공유할 때는 **모델과 리비전, 장비와 칩 수, 부하, 지연 목표, 선택한 설정, 처리량, 반복 횟수, 품질 상태**를 함께 기록한다. [필수 입력 열과 로그 사전](data-contract.md)
